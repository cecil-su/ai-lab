# 小说运行时层（连载控制环）

六层准备包（`skills/novel-*`）回答"动笔前备什么"——全是 **design-time 静态契约**。但一本书 99% 的工作量在"**正在写第 247 章**"。这一层补的就是 **runtime**：把六层契约在连载期串成一个**每章维护的控制环**。

> 它不是开工准备包的第⑦层，而是把六层在连载期跑起来、并对抗"边写边崩"的控制层。把 `docs/notes/2026-06-01-创作流程编排.md` §阶段三升级成正式控制环。

**语言：** 跟随用户，默认中文。

## 四种模式

| 模式 | 干什么 | 触发 |
|---|---|---|
| **建状态**（开工时） | 初始化运行时状态文件（4 store + 看板 + 读者口） | "建运行时状态" |
| **装配**（写新章前） | 按配方检索切片，拼出本章 prompt 上下文 | "装配第 N 章上下文" |
| **tick**（写完一章后） | 抽取→人工确认→喂回，更新 4 store | "这章写完了""跑一次维护" |
| **看板**（任意时刻） | 出 5 张图，查漂移 | "看仪表盘""查漂移" |

---

## 运行时状态：四个 store（机械 ↔ 人工光谱）

这是本层的核心数据。**四个 store 数据结构、失效模式各不相同，不合并成一张表**——统一的是下面的 tick 控制环，不是数据。

| store | 数据结构 | 写语义 | 自动化 | 归属 |
|---|---|---|---|---|
| 角色状态表 | 寄存器/KV | 覆盖（最新值赢） | LLM 抽 + 人工确认 | ⑥ 表 A |
| 名词表 | append-only 字典 | 插入、几乎不改 | LLM 抽 + 人工确认 | ⑥ 表 B |
| **伏笔台账** | 带 TTL 的工单队列 | open → resolve/过期 | **人为主**，LLM 只到期提醒 | ⑥ 表 C |
| **语言指纹** | 滑动窗口频率 | 衰减累加 | **纯计算 daemon** | `lab/novel-fingerprint/` |

> 光谱两端：语言指纹**无需人工确认**（算出来的），伏笔的"是不是伏笔"是作者意图、文本测不出（**LLM 抽不出，只能提醒**）。中间两个走 ⑥ 的"抽 + 确认"铁律。

---

## tick：每章维护循环（extract → commit → feed-forward）

写完一章后跑一圈。这是 §阶段三的正式化：

1. **装配 + 生成**：按下方配方拼上下文 → 注入 ⑤ 风格前缀 → 生成本章。
2. **⑤ 审计（conformance）**：试金石 + 八维 + 禁忌。跑味回 1。
   > 注意：审计只验"符不符合自己定的契约"，**不验好不好看**（见 novel-style 模式三）。它是语言指纹 daemon 抓不到的**主题层趋同**的语义兜底。
3. **语言指纹 daemon**：`node lab/novel-fingerprint/fingerprint.mjs 近N章 最新章 --names <名词表导出>`。WARN（退出码 2）→ 按提示改写最新章（避开章末口头禅/高频词）。
4. **extract**：LLM 从本章抽三类候选——①状态变更 ②新专有名词 ③伏笔（本章埋了什么 / 回收了哪条）。指纹不在此列（自动）。
5. **commit**：逐条**人工确认**才入 ⑥ 三表。LLM 抽错不许自动入库（70-80% 准确率）。指纹自动入。
6. **feed-forward**：更新看板 → 下一章回 1。

## 装配（写新章前的上下文配方）

长文生成真正的难题：第 247 章塞什么进 prompt？前 246 章 + 全部契约**塞不下**。原则：**按需检索切片，不是全量塞**——前缀越长越稀释。

本章上下文 = 拼下面几块：

- **固定前缀**：⑤ 风格契约前缀（~9 行）+ **反重复指令**（来自上一次指纹 WARN：避开最近高频词与章末口头禅）。
- **当前状态切片**：⑥ 表 A 里**本章涉及的角色**的当前值（境界/伤势/关系），不是全表；⑥ 表 B 里**本章会用到的**名词。
- **到期伏笔**：⑥ 表 C 中回收窗口落在本章附近的条目 →"该回收 X"。
- **本章章纲**：④ 对应章纲（含可选"关键节拍 3-5 条"）。
- **近场记忆**：最近 1-2 章的结尾段，保连贯——不是全文。

## 看板（5 张生成型图）

系统默认**零可观测**——漂移要等你读到才发现。这 5 张图是 store 的视图，每张都回答"我下一章该注意什么"：

1. **战力/境界曲线**（轨迹·⑥表A境界 对章序）——抓节奏病（升太快没张力 / 太平没爽点）。
2. **节拍/爽点分布**（轨迹·④）——抓两高潮挨太近 / 长平谷。
3. **伏笔弧线**（轨迹·⑥表C）——每条伏笔一根"埋设章→回收章"箭头；悬空的箭头 / 超期的长箭头一眼看出。
4. **演变关系图谱**（时间切片·⑥表A关系）——抓悬空节点（某角色 N 章没出场）/ 关系无过渡突变。
5. **双轨时间线**（故事时间 vs 叙述时间）——**王图**：两轨的偏移量就是伏笔/回忆/插叙/反转的栖身处，唯一能同时管理所有结构性张力的视图。

能**自动画**的（境界/节拍/伏笔/指纹）vs 需**人工喂**的（关系为什么变）——继承上面的机械↔人工光谱。

## 读者信号口（预留，现在为空）

连载真正的控制环里有**读者反馈**（追读率/评论情绪/弃书点）。它现在没上线，但**预留入口**，等真上连载再插：

- **输入**：每章追读率、评论情绪、弃书点——**真数据**。
- **用途**：喂回 ④ 调后续章纲、① 校爽点密度。
- **边界**：这里只留**真实数据**的口子；**不做读者模拟**（persona ≠ 真读者，是远期方向 B，见项目 memory）。留口正是为了避开"靠模拟凑信号"这条坑。

## 文件与边界

| 文件 | 作用 |
|---|---|
| `template.md` | 运行时状态文件框架（4 store 索引 + 看板快照 + 读者口） |
| `examples/fanren.md` | 一次 tick 的完整演示（含指纹抓出"慢慢来"章末口头禅） |
| `docs/runtime/<slug>.md` | 用户的运行时状态（每本书一份，持续更新） |

- **与 ⑥ 的边界**：⑥ 定义三张表的 schema 和"抽+确认"铁律（**表长什么样**）；runtime 是把 ⑥ + ⑤审计 + 指纹daemon + ④章纲 在**每章串起来转一圈**的控制环（**每章怎么转**）。
- **上游**：六层准备包全部。
- **不做**：全自动发布（章节 agent 出草稿供人类改写）；读者模拟；自动伏笔回收判定（只提醒，人决定）。
