# Harden agent-roundtable's file-protocol invariants instead of adopting a database

agent-roundtable persists a discussion as a topic directory of plain files: `transcript.jsonl` (append-only speeches), `topic.json` (round/status/sessionRef/tokens), `inbox.jsonl` + `inbox.cursor` (pending commands), and `summary.md` (final artifact). An architecture review (2026-07-30) correctly observed that the reliability of this model rested on unenforced assumptions and that a single speech or finalization spans several file writes with no atomicity, generation, or recovery protocol, so a crash between steps forks state that recovery can only guess at.

The concurrency model we commit to is **hybrid**, not "single writer" across the board:
- **transcript / topic.json — single writer.** Exactly one runner owns a topic at a time, enforced by an atomic `openSync(...,"wx")`/O_EXCL lock (not the old read-check-write). Speeches and status are written only by that runner.
- **inbox — multi-writer-safe, not single-writer.** Multiple producers (the attached TUI, `stop`, `continue --ask`) may write concurrently. Safety comes from a cross-process short lock (`inbox.lock`, `wx`) serializing appends plus a physical-line cursor for consumption, so no producer needs to hold the runner/attach lock and concurrent writes cannot lose or alias events.

  Boundary to record explicitly: `withInboxLock` is **fail-open** — after a 2s acquisition timeout (or on lock-file error) it proceeds without the lock (best-effort). Under that rare degradation two appends can byte-interleave; a torn line is then tolerated by the reader (counted as a bad physical line, skipped, cursor still advances) rather than corrupting the cursor. So the guarantee is "serialized appends up to 2s of contention, torn-line-tolerant beyond that", not "unconditionally serialized".

We will **not** respond by moving to SQLite, a WAL, or event-sourcing. This is a single-user local CLI: a crash lands between two writes for one topic, the blast radius is that one topic, and the human operator is present to re-run `continue`. The cost of a database or full event log is not justified by that failure model. Instead we harden the existing file model in place: atomic lock acquisition (`openSync` `wx`/O_EXCL, done), a cross-process short lock plus physical-line cursor making the inbox multi-writer-safe rather than single-writer (done), whole-process-tree termination on timeout/error (done), a persisted `finalizing`/generation marker so finalization is crash-idempotent, and — as a later phase — treating `transcript.jsonl` as the recovery source with `topic.json` demoted to a rebuildable checkpoint/projection.

The consequence we accept: recovery guarantees are bounded by "resume from the append-only log to the last durable checkpoint", not full transactional integrity. This rests on the current failure model — local, single-user, foreground execution where a human is present to observe a crash and re-run `continue`.

**Re-review triggers** (any one invalidates the decision): the "human is present to re-run" assumption breaks the moment roundtable runs unattended. Revisit this ADR — and reconsider a real event log or database — when roundtable moves to **multi-user or server-hosted use, a background/daemon mode, unattended/scheduled automation, or a remote runner**. Until one of those holds, the directory model stays and reliability comes from enforcing invariants, not from new infrastructure.
