# 代理协议对比:从 Shadowsocks 到 Hysteria2

> 整理日期:2026-06-24
> 主题:科学上网代理协议的设计思路、抗封锁能力与选型

## 一、核心三协议

### Shadowsocks (SS)
- **本质**:加密的 SOCKS5 代理。客户端与服务端用预共享密码做对称加密(如 `aes-256-gcm`、`chacha20-poly1305`)。
- **流量特征**:加密后是高熵的随机字节流,没有明显协议头。早期是优点(不像任何已知协议),后来成了缺点——"全程随机、没有 TLS 握手"本身就是特征,可被主动探测 + 流量统计识别。
- **定位**:轻量、快、实现简单。在没有 DPI 深度封锁的环境里依然够用。
- **衍生**:SSR 加了混淆插件;后来主流是 SS + `v2ray-plugin` / `simple-obfs` 套一层伪装。

### Trojan
- **核心思路**:不混淆,而是"假装成正常 HTTPS"。流量本身就是真正的 TLS,跑在 443 端口,需要真实域名 + 证书。
- **工作方式**:客户端先建立标准 TLS 连接,在 TLS 内部发送密码。密码对了就代理;密码错了或被主动探测,服务器把请求转发给后面真实的网站(fallback),探测者看到的就是一个正常网站。
- **抗封锁**:对 DPI 来说,它和访问任何 HTTPS 网站无法区分(除非封整个 TLS)。这是它比 SS 强的地方。
- **代价**:需要域名和证书,部署比 SS 麻烦。

### AnyTLS
- **背景**:较新的协议,针对 TLS 代理的一个老问题——TLS-in-TLS 嵌套导致的流量指纹。当你在 TLS 里再包一层 TLS(比如访问 HTTPS 网站)时,数据包大小分布会呈现可被机器学习识别的特征。
- **解决思路**:在应用层做数据包分片/填充(padding)调度,主动打乱包长分布,削弱 TLS-in-TLS 指纹;同时支持连接复用(multiplexing),减少频繁建连的开销和特征。
- **定位**:可理解为"针对最新检测手段做了优化的 TLS 代理",目标是比 Trojan 更难被流量分析识别。客户端支持以 sing-box、mihomo(Clash.Meta)为主。

### 三者速览

| 维度 | Shadowsocks | Trojan | AnyTLS |
|------|-------------|--------|--------|
| 伪装思路 | 加密成随机流 | 伪装成真 HTTPS | 真 HTTPS + 抗流量指纹 |
| 是否需要域名/证书 | 否 | 是 | 是 |
| 抗 DPI/主动探测 | 弱~中(需配插件) | 强 | 强(且针对 TLS-in-TLS 优化) |
| 部署难度 | 低 | 中 | 中 |
| 成熟度/生态 | 最成熟 | 成熟 | 较新 |

**演进逻辑**:SS 解决"加密 + 不像已知协议" → Trojan 解决"主动探测"(变成真 HTTPS) → AnyTLS 解决"TLS 嵌套的流量统计指纹"。越往后越针对更高级的检测手段,也越依赖真实域名/证书这套基础设施。

## 二、放进整个协议生态:三代演进

### 第一代:加密混淆(藏起来)
- **Shadowsocks / SSR** — 加密成随机流,目标是"不像任何已知协议"。

### 第二代:TLS 伪装(假装成正常网站)
共识是:与其藏,不如变成真 HTTPS。区别在"传输内核"和"伪装精细度"。

- **VMess**(V2Ray 原生协议)
  - 老牌,自带加密 + 时间戳防重放。
  - 缺点:协议本身有特征,且有自己的加密层(冗余),性能和隐蔽性都不如后辈。现已基本被 VLESS 取代。

- **VLESS**
  - VMess 的"减负版":去掉自带加密,把安全完全交给外层 TLS。
  - 本身只是轻量传输协议,真正的隐蔽性靠搭配的传输层,最重要的是 **XTLS Vision / REALITY**:
    - **REALITY** 是当前最强方案之一——不需要自己买域名证书,而是"借用"别人真实的大网站(如 `www.microsoft.com`)做 TLS 握手伪装,探测者甚至会被导向那个真网站。解决了 Trojan"必须自备域名+证书,且证书/域名本身可能成为线索"的问题。

- **Trojan**
  - 思路同 VLESS+TLS,但更简单直接:TLS 里塞密码 + fallback。
  - 与 VLESS 的差别更多是"实现风格",抗封锁能力上 VLESS+REALITY 现在普遍被认为更强。

- **AnyTLS**
  - 针对 TLS-in-TLS 流量指纹做 padding + 多路复用优化。属于这一代里"查漏补缺"的新选手。

### 第三代:基于 UDP/QUIC 的抗丢包(换传输底座)
前两代都是 TCP。这一代换成 UDP,主打弱网/高丢包环境下的速度。

- **Hysteria / Hysteria2**
  - 基于 QUIC,自带魔改的拥塞控制(可"暴力"抢带宽),在丢包严重的国际线路上速度远超 TCP 系。
  - 伪装成 HTTP/3 流量。代价:UDP 容易被 QoS 限速甚至阻断,且"抢带宽"对共享线路不友好。

- **TUIC**
  - 同样基于 QUIC,设计更"温和规矩",和 Hysteria 是同一赛道的两个选择。

## 三、选型实用结论

| 场景 | 推荐 |
|------|------|
| 追求最强抗封锁、不想买域名 | **VLESS + REALITY** |
| 已有域名证书、想要简单稳定 | Trojan 或 VLESS + XTLS |
| 担心 TLS 嵌套被流量分析 | AnyTLS |
| 国际线路丢包严重、要速度 | **Hysteria2** / TUIC |
| 环境宽松、只要轻量快 | Shadowsocks |

**一句话主线**:

```
SS(藏)
  → VMess / VLESS / Trojan(假装 HTTPS)
    → REALITY / AnyTLS(连证书和 TLS 指纹都伪装好)
      → Hysteria2 / TUIC(干脆换 UDP 拼速度)
```

客户端层面,现在 **sing-box** 和 **mihomo(Clash.Meta)** 两个内核基本把上面所有协议都支持了,所以选协议主要看服务器环境和线路质量,而不是客户端。

## 四、配置示例

以下均以 **sing-box** 格式为例(服务端 + 客户端各一份)。占位符 `<...>` 替换成自己的值,密钥/UUID 用工具生成,不要手填。

### 4.1 VLESS + REALITY

**生成所需材料**:

```bash
sing-box generate uuid                 # 得到 UUID
sing-box generate reality-keypair      # 得到 PrivateKey / PublicKey
sing-box generate rand --hex 8         # 得到 short_id(可选,多个)
```

> REALITY 的关键是"借"一个真实大站做握手伪装,这里以 `www.microsoft.com:443` 为例,要求:该站支持 TLS 1.3 + H2,且在你服务器到它的网络可达。

**服务端**(`server: handshake_server` / `private_key` 不外泄):

```jsonc
{
  "inbounds": [
    {
      "type": "vless",
      "listen": "::",
      "listen_port": 443,
      "users": [
        { "uuid": "<UUID>", "flow": "xtls-rprx-vision" }
      ],
      "tls": {
        "enabled": true,
        "server_name": "www.microsoft.com",
        "reality": {
          "enabled": true,
          "handshake": {
            "server": "www.microsoft.com",
            "server_port": 443
          },
          "private_key": "<REALITY_PRIVATE_KEY>",
          "short_id": ["<SHORT_ID>"]
        }
      }
    }
  ]
}
```

**客户端**(`public_key` 对应服务端的 private_key):

```jsonc
{
  "outbounds": [
    {
      "type": "vless",
      "server": "<服务器IP或域名>",
      "server_port": 443,
      "uuid": "<UUID>",
      "flow": "xtls-rprx-vision",
      "tls": {
        "enabled": true,
        "server_name": "www.microsoft.com",
        "utls": { "enabled": true, "fingerprint": "chrome" },
        "reality": {
          "enabled": true,
          "public_key": "<REALITY_PUBLIC_KEY>",
          "short_id": "<SHORT_ID>"
        }
      }
    }
  ]
}
```

要点:
- 客户端 `server_name`、`short_id` 必须和服务端一致;`public_key` 与服务端 `private_key` 配对。
- `utls.fingerprint` 让 TLS ClientHello 伪装成真实浏览器(如 chrome),进一步降低指纹。
- `flow: xtls-rprx-vision` 两端要一致,这是 XTLS 的零拷贝直连,降低 TLS-in-TLS 开销。

### 4.2 Hysteria2

**生成所需材料**:Hysteria2 需要 TLS 证书。两种方式:
- 自有域名:用 `acme` 自动签发(下例服务端走 acme)。
- 无域名:自签证书 + 客户端开 `insecure`(测试可用,正式环境不推荐)。

**服务端**(自有域名 + acme 自动证书):

```jsonc
{
  "inbounds": [
    {
      "type": "hysteria2",
      "listen": "::",
      "listen_port": 443,
      "users": [
        { "password": "<密码>" }
      ],
      "tls": {
        "enabled": true,
        "server_name": "<你的域名>",
        "acme": {
          "domain": ["<你的域名>"],
          "email": "<你的邮箱>"
        }
      }
    }
  ]
}
```

**客户端**:

```jsonc
{
  "outbounds": [
    {
      "type": "hysteria2",
      "server": "<你的域名>",
      "server_port": 443,
      "password": "<密码>",
      "up_mbps": 50,
      "down_mbps": 200,
      "tls": {
        "enabled": true,
        "server_name": "<你的域名>"
      }
    }
  ]
}
```

要点:
- `up_mbps` / `down_mbps` 填你**本地实际带宽**(单位 Mbps),Hysteria2 的拥塞控制据此调度。填得太高会"抢带宽"伤害线路,填得太低则跑不满。
- 走 acme 时服务器 443 端口要能被 Let's Encrypt 访问以完成验证;之后正常代理流量伪装成 HTTP/3。
- 自签证书场景:服务端 `tls` 改成本地 `certificate_path` / `key_path`,客户端 `tls` 加 `"insecure": true`(跳过证书校验,仅测试用)。
- UDP 协议,注意服务商/线路是否对 UDP 限速或阻断;若被 QoS,回退到 TCP 系(VLESS+REALITY)。

> 提示:以上为最小可用配置,省略了 `log`、`dns`、`route`、本地 `mixed`/`tun` 入站等。实际使用时客户端还需要一个本地入站(如 `mixed` 监听 socks/http,或 `tun` 透明代理)把流量导入 outbound。

### 4.3 mihomo(Clash.Meta)客户端 YAML

mihomo 主要做客户端,服务端仍用上面的 sing-box(或 Xray)。下面是同样两个协议在 mihomo 里的 `proxies` 写法,字段值要和服务端对应。

```yaml
# ---- 基础(本地入站 + 模式)----
mixed-port: 7890        # 本地 socks/http 混合入站
allow-lan: false
mode: rule
log-level: info

proxies:
  # ---- VLESS + REALITY ----
  - name: "vless-reality"
    type: vless
    server: <服务器IP或域名>
    port: 443
    uuid: <UUID>
    network: tcp
    udp: true
    tls: true
    flow: xtls-rprx-vision
    servername: www.microsoft.com        # 对应服务端 server_name
    client-fingerprint: chrome           # 对应 sing-box 的 utls fingerprint
    reality-opts:
      public-key: <REALITY_PUBLIC_KEY>   # 对应服务端 private_key
      short-id: <SHORT_ID>

  # ---- Hysteria2 ----
  - name: "hysteria2"
    type: hysteria2
    server: <你的域名>
    port: 443
    password: <密码>
    sni: <你的域名>                       # 对应服务端 server_name
    up: "50 Mbps"                         # 本地实际上行带宽
    down: "200 Mbps"                      # 本地实际下行带宽
    # skip-cert-verify: true             # 仅自签证书测试时打开,对应 sing-box 的 insecure

# ---- 分组与规则(最小示例)----
proxy-groups:
  - name: "PROXY"
    type: select
    proxies:
      - vless-reality
      - hysteria2

rules:
  - GEOIP,CN,DIRECT
  - MATCH,PROXY
```

要点(与 sing-box 字段对照):
- `servername` / `sni` = sing-box 的 `server_name`;两端必须一致。
- `reality-opts.public-key` = 服务端 `private_key` 配对出来的公钥;`short-id` 两端一致。
- `client-fingerprint: chrome` 等价于 sing-box 客户端的 `utls.fingerprint`。
- Hysteria2 的 `up`/`down` 带单位字符串(如 `"50 Mbps"`),含义同 sing-box 的 `up_mbps`/`down_mbps`,填本地真实带宽。
- mihomo 自带本地入站(`mixed-port`)和路由规则,不像 sing-box 那样还要单独配 inbound;装好这份 YAML 基本即用。
